# Собственный генератор кубиков

Рабочая изолированная программа на Node.js 24, без аккаунтов, внешних API и новых зависимостей. Её файловый журнал **не используется production**. Для подключения алгоритма подготовлена отдельная реализация SQL/координатор/браузер v37, которая не меняет протокол существующих drand-комнат. [Описание production-интеграции](../../docs/system-fair-dice-v37.md). Подготовка RANDOM.ORG остаётся отдельной и неактивной.

Быстрый запуск из корня проекта:

```sh
node experiments/system-dice/program.js demo
node experiments/system-dice/program.js demo 1000
node --test tests/system-dice*.test.js
```

`demo` действительно генерирует значения, рассчитывает две физические кости и проверяет доказательство. В отчёте есть пример, частоты 36 упорядоченных пар и локальное время вычисления. Это **не** измерение задержки сайта: сеть, сохранение журнала и анимация в этот замер не входят. Частоты — диагностика, а не доказательство случайности. Оба участника демонстрации работают в одном процессе; для защиты от подбора сервером клиентский вклад должен поступать от отдельного браузера.

Проверка 18 сентября: 60 тестов этого генератора прошли, 2 проверки неверного владельца файла/папки пропущены без root, ошибок нет. Существующие 188 fair-dice тестов тоже прошли. Отдельный локальный замер **с записью и fsync журнала** на 1000 бросках: p50 39,08 мс, p95 55,01 мс, максимум 87,18 мс; сеть, браузер, production SQL и анимация исключены. [Полный отчёт и границы измерения](validation-2026-09-18.json).

## Генерация и проверка

Источник начального секрета — `crypto.randomBytes(32)`, криптографически стойкий генератор операционной системы ([официальная документация Node.js](https://nodejs.org/api/crypto.html#cryptorandombytessize-callback)). `Math.random()`, часы, рейтинг, никнейм, выбор стратегии бота и состояние выигрышности не используются как источник случайности. Хеш позиции входит только в неизменный контекст броска.

Порядок действий обязателен:

1. Сервер сохраняет новый 32-байтный секрет и возвращает обязательство SHA-256, привязанное к комнате, партии, номеру и позиции. Секрет пока не раскрывается.
2. Браузер получает и сохраняет это обязательство, **только затем** создаёт свежие 32 байта через `crypto.getRandomValues()`. Для каждого броска нужен новый непредсказуемый вклад, а не постоянный seed или значение из номера хода.
3. Сервер сохраняет первый принятый клиентский вклад и рассчитывает HMAC-SHA256. Значения байтов 252–255 пропускаются; первые два подходящих байта дают кости `(байт % 6) + 1`. Среди 252 принятых значений каждому числу соответствует ровно 42 байта: преобразование не вносит модульного смещения.
4. Сервер раскрывает секрет и результат. Проверяющий сверяет секрет с **ранее полученным** обязательством, клиентский вклад с **собственным сохранённым** значением, затем полностью пересчитывает кости.

Обычный дубль не перебрасывается. Только ничья стартового броска разрешается детерминированным увеличением счётчика; проверка требует первый допустимый результат, а не выбранный сервером счётчик. Подбор нового секрета для уже занятого номера и смена принятого клиентского вклада запрещены журналом. Секреты разных бросков независимы: раскрытие текущего не раскрывает следующий.

Для броска бота вклад тоже должен создавать **браузер человека**, после получения обязательства. Если оба секрета создаёт сервер, это обычная серверная генерация, а не защита от самого оператора. Для полностью автономных ботов независимость от оператора потребует внешнего источника.

## Протокол

Идентификатор `nardu/system-dice/v1`. Контекст имеет ровно семь полей: `gameId` (нижнерегистровый UUID), `nonce` (безопасное целое от 1), `roomCode` (`XXXX-XXXX`), `variant` (`long`/`short`), `label` (`opening`/`roll`), `color` (`none` для старта, иначе `white`/`dark`), `positionHash` (64 символа lowercase hex).

Канонический контекст — точный UTF-8 JSON-массив:

```text
["nardu/system-dice/v1",gameId,nonce,roomCode,variant,label,color,positionHash]
```

Обязательство:

```text
SHA256(UTF8(JSON.stringify(["nardu/system-dice-commitment/v1",canonicalContext,serverSeedHex])))
```

Блок потока для счётчика и блока, начиная с нулей:

```text
HMAC-SHA256(key=hexDecode(serverSeedHex),
  message=UTF8(JSON.stringify(["nardu/system-dice-hmac/v1",canonicalContext,clientSeedHex,counter,block])))
```

Нужны минимальное количество блоков для двух подходящих байтов и минимальный допустимый счётчик. При исчерпании ограниченного потока программа выдаёт отказ, а не новый случайный бросок. `verifyProof(proof, {context, commitment, clientSeed})` требует внешние ожидаемые данные: копирование этих данных из самого доказательства не подтверждает предварительную фиксацию.

## Постоянный журнал и CLI

`program.js --help` показывает команды `init`, `prepare`, `client-seed`, `reveal`, `verify`, `demo`. Команды с файлами требуют абсолютные пути. Программа выводит публичный результат в stdout; `prepare` никогда не выводит секрет. `reveal` раскрывает только секрет принятого броска.

`init /absolute/new/private-directory` создаёт **новую** папку 0700; родитель уже должен существовать. Существующая папка не захватывается и её права не меняются. Путь не должен содержать символических ссылок; на macOS используйте `/private/tmp`, а не `/tmp`. Записи имеют права 0600 и принадлежат текущему пользователю. Не размещайте журнал в каталоге, раздаваемом веб-сервером, не публикуйте его и защищайте резервную копию.

Для `prepare DIR CONTEXT.json` нужен JSON-контекст, например:

```json
{
  "gameId": "11111111-1111-4111-8111-111111111111",
  "nonce": 1,
  "roomCode": "DEMO-0001",
  "variant": "long",
  "label": "roll",
  "color": "white",
  "positionHash": "abababababababababababababababababababababababababababababababab"
}
```

Сохраните ответ `prepare` как публичную квитанцию. Только после этого команда `client-seed` создаёт объект `{"clientSeed":"64-символьное hex-значение"}`. Это средство локального тестирования, не замена браузерному участнику в реальной партии. `reveal DIR CONTEXT.json RECEIPT.json CHALLENGE.json` возвращает доказательство. Для `verify PROOF.json EXPECTED.json` второй файл содержит ровно `{context, commitment, clientSeed}`, сохранённые проверяющей стороной раньше, а не переписанные из доказательства после броска.

Журнал уникален по `(gameId, nonce)`. Другой контекст для того же номера отвергается. Повторный запрос и новый экземпляр программы используют прежний секрет и результат. Принятие первого клиентского вклада сохраняется до расчёта/раскрытия; после сбоя вычисление продолжается с теми же данными. Запись выполняется с fsync; изменения — атомарной заменой файла. Одновременные операции блокируются отдельным эксклюзивным lock-файлом; `DICE_BUSY` означает повторить **ту же** операцию позже, не получить другой номер.

Аварийно завершившийся процесс может оставить lock-файл. Программа не снимает его по таймеру и не создаёт новый бросок. Восстановление требует оператора, который удостоверится, что прежний процесс действительно остановлен, сохранит журнал и восстановит доступ именно к прежней записи. Удаление записи, rollback старой копии или новый `gameId` для неудобного результата запрещены правилами интеграции. Это частный однохостовый журнал, не авторизованный многосерверный SQL-сервис.

## Что можно утверждать игроку

После успешной проверки корректен статус:

> Проверка пройдена. Исходный секрет соответствует ранее полученному обязательству. Кости рассчитаны верно с использованием вашего сохранённого случайного вклада.

Некорректен статус «независимый источник подтверждён»: здесь нет независимой подписи drand/RANDOM.ORG. Проверка не доказывает физическую случайность одного броска, время публикации обязательства без клиентской записи или невозможность оператору намеренно прекратить ответ/партию (selective abort). Подпись нашего сервера могла бы удостоверять квитанцию, но не устранит эти ограничения. Скрывать их или выдавать собственный генератор за независимый нельзя.

## До подключения к порталу

Нужны отдельная версия протокола в SQL, серверная авторизация и CAS по состоянию комнаты, запрет пропусков/отмены номеров, доставка и сохранение обязательства в браузере, браузерная проверка, журнал сорванных/отменённых бросков, сохранение доказательств, защита от выборочного прекращения и правила таймаута. Клиент человека должен вносить случайность также в броски бота. Старые доказательства drand остаются проверяемыми своим протоколом, fallback между источниками посреди комнаты запрещён.

После этого проверяются реальная задержка HTTPS от нажатия до отображения костей (включая оба запроса, сохранение и анимацию), конкурентные вкладки, рестарт, мобильные браузеры и нагрузка. Цель ≤2 секунды достижимостью этого прототипа **ещё не подтверждена**. Публикация и смена production-источника в эту подготовку не входят.
