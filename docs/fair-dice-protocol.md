# Проверяемые броски во время игры — v36

Выпуск v36 включает SQL-миграцию, отдельный координатор и совместимый фронтенд. Новый режим включается для новых комнат только после проверки всех трёх частей. Изменение текста старой проверки само по себе не создаёт доказательства.

## Что увидит игрок

Для нового подписанного броска успешная проверка показывает:

> Проверка пройдена
>
> Источник броска подтверждён, кости рассчитаны верно.
>
> Источник случайного значения — независимый drand, а не игрок или бот. Протокол броска одинаков для игроков и ботов.

Этот статус выдаётся только после локальной проверки BLS-подписи независимого источника, Ed25519-подписи закреплённой серверной записи, полного SHA-256 и обеих записанных костей. Смена кости, подписи, комнаты, назначения броска или игровой сессии не превращается в успешную проверку. Полные значения можно раскрыть и скопировать, не отправляя их стороннему сайту.

Исторические SHA-256-броски остаются проверяемыми на соответствие хешу, но не получают значок подтверждённого независимого источника. Отсутствие исторического доказательства не является свидетельством фальсификации; восстановить несуществовавшую подпись нельзя.

## Откуда берутся кости

1. База под блокировкой комнаты фиксирует единственную запись броска: UUID запроса, комнату, UUID партии, последовательный номер, назначение, цвет, вид нард, хеш полного сохранённого состояния, серверное время и **будущий** раунд drand quicknet. Первый номер — 1.
2. Будущий раунд выбирается относительно часов PostgreSQL с запасом шесть секунд. Период quicknet — три секунды; ожидаемая задержка нового броска около 6–9 секунд плюс доставка и проверка. Это цена предварительного закрепления неизвестного результата; не измерение production-производительности.
3. Координатор возвращает подписанную Ed25519 запись и получает только закреплённый раунд с официальных HTTP-реле. Проверяется настоящая BLS-подпись quicknet с закреплёнными параметрами цепи. Ответ реле без правильной подписи отвергается.
4. Из подписанного значения детерминированно рассчитывается SHA-256 и две кости. После сохранения доказательства сервер разрешает только соответствующий бросок и законные переходы состояния по действующим правилам `game.js`.
5. Повторный запрос, перезагрузка браузера, смена реле или рестарт координатора продолжают **ту же** запись. Новый номер вместо неудобных костей не выдаётся. Выход из начатой партии — завершение по действующим правилам, а не отмена результата ради переброса.

Ни сложный бот, ни обычный игрок не передают серверу свои выбранные кости. В защищённой комнате прямой UPDATE игрового JSON, смена протокола, подмена присутствия или удаление начатой комнаты не обходят серверную проверку. Стратегия и веса ботов не изменяются.

## Точный протокол

Идентификатор: `drand-quicknet-v1`.

Закреплённая цепь: `52db9ba70e0cc0f6eaf7803dd07447a1f5477735fd3f661792ba94600c84e971`.

Генезис: `1692803367` Unix-секунд; период: `3` секунды; схема: `bls-unchained-g1-rfc9380`. Публичный BLS-ключ и все параметры находятся в `fair-dice.js`; HTTP `latest` не используется. Подпись — 48 байт в G1, ключ — 96 байт в G2. Сообщение подписи — SHA-256 от восьмибайтного big-endian номера раунда, затем RFC9380 hash-to-G1 с DST `BLS_SIG_BLS12381G1_XMD:SHA-256_SSWU_RO_NUL_`.

Каноническая строка записи — точный UTF-8, десять строго проверенных полей, без нормализации произвольного ввода:

```text
nardu/drand-quicknet/v1|id|roomCode|gameId|nonce|label|color|variant|round|createdAt|positionHash
```

`createdAt` — ISO UTC с миллисекундами. `label` — `opening` или `roll`; цвет стартового броска — `none`. `positionHash` вычисляется **PostgreSQL от полного JSONB::text сохранённого состояния** и передаётся как непрозрачное обязательство; браузер не подменяет его собственным JSON.stringify. Подписывается SHA-256 канонической строки. Доверенный публичный Ed25519 ключ координатора поступает из конфигурации опубликованного клиента, а не из вставленного доказательства.

`randomness = SHA256(декодированная BLS-подпись)`.

Вход для конечного SHA-256:

```text
каноническая строка|randomness|counter
```

Счётчик начинается с 0. Первые два байта SHA-256 меньше 252 дают физические кости по формуле `(байт % 6) + 1`; 252–255 пропускаются. При недостатке байтов или стартовом дубле счётчик увеличивается детерминированно, без RNG. Обычный дубль не перебрасывается: две физические кости становятся четырьмя возможностями хода. При неисправности источника нет запасного генератора: партия ожидает тот же результат.

Каждая запись истории хранит `fairDiceProof`, полный `sha256Input`, хеш и кости. Проверка всей истории дополнительно сверяет контекст комнаты, эпоху, назначение, цвет и непрерывность номеров. Доказательство не переносится на соседнюю комнату или реванш. Проверка бросков не оценивает силу ходов.

## Что доказывается и что не обещается

Криптографическая проверка подтверждает происхождение независимого значения и точный расчёт данных этого броска. Серверный журнал и проверка переходов исключают выбор костей игроком/ботом через штатный клиент или прямые запросы от их учётных данных.

Ни одна зелёная надпись не должна обещать математического доказательства физической случайности отдельного броска. Подпись сервера сама по себе не является внешним свидетельством времени её публикации: доверие к оператору, серверным часам, закреплённому клиенту и инфраструктуре остаётся. Компрометация административного доступа, серверного ключа, поставки клиента или достаточного числа участников drand — отдельная модель угроз. Для независимого аудита оператора потребуется внешняя своевременная публикация обязательств, не только собственный журнал.

Ключ подписи должен сохраняться между рестартами. Его нельзя менять при каждом развёртывании. Первичная версия использует один закреплённый ключ; перед будущей ротацией необходим совместимый каталог исторических ключей, иначе старые квитанции перестанут подтверждаться новым клиентом. Для первого выпуска такой ротации нет.

## Безопасный выпуск

Реальный production использует Caddy **в Docker**, сеть `supabase_default`, внутренний Kong. Координатор на host-loopback без дополнительной маршрутизации Caddy недоступен. Подготовлены `ops/timeweb/fair-dice.Dockerfile`, `fair-dice.compose.yml` и фрагмент `fair-dice.caddy`: отдельный непривилегированный контейнер, без опубликованного порта, в существующей сети. Привязка `0.0.0.0` разрешена скриптом только явно внутри контейнера; обычный запуск остаётся на `127.0.0.1`.

Порядок выпуска после разрешения:

1. Снять резервную копию PostgreSQL и точных Caddy/Compose-конфигураций. Зафиксировать прежние версии и проверить доступность восстановления. Не выводить `.env`, токены, дамп базы или ключи в журнал задачи.
2. На PostgreSQL выполнить миграцию и `supabase/tests/fair-dice-v36-rollback-smoke.sql` в транзакции с откатом. Проверить также реальные зарегистрированные и гостевые роли, рейтинги, создание/закрытие комнаты, присутствие, выход, реванш и конкурирующие вкладки. Статические SQL-тесты не заменяют эту проверку.
3. Применить `supabase/fair-dice-v36.sql` **с выключенной политикой**. Не переименовывать существующие партии в новый протокол и не подделывать их доказательства.
4. Создать один Ed25519 секрет из системного CSPRNG: 32 байта hex, отдельный файл `/etc/online-backgammon/fair-dice-signing.key`, владелец UID 10001, права 0600, без символических ссылок. Защитить резервную копию. Наружу публикуется только производный публичный ключ.
5. Проверить и закрепить digest официального Node.js 24 контейнера; передать его через `FAIR_DICE_NODE_IMAGE`. Собрать точный проверенный release. Проверить Docker-сетевой доступ к Kong и подписанный будущий раунд; не публиковать результат `docker compose config` с интерполированными секретами. Внутренний Kong использует серверный `ANON_KEY`; публичный браузерный `sb_publishable_…` задаётся отдельно через `SUPABASE_PUBLISHABLE_KEY`. Только точное совпадение этой гостевой ссылки на ключ с парой гостевых заголовков переводится в внутренний anon JWT; доказательство гостевой сессии всё равно проверяет SQL. JWT зарегистрированного игрока не заменяется.
6. Добавить Caddy `handle /fair-dice/v1/*` **до** существующего catch-all, не используя `handle_path`. Проверить конфигурацию, перезагрузить Caddy и проверить HTTPS, CORS, прежние auth/API маршруты. Браузерная база URL: `https://api.201-51-7-193.sslip.io/fair-dice/v1`.
7. При выключенной общей политике создать только отдельные контролируемые гостевые canary-комнаты: временное включение и восстановление OFF выполняются в одной транзакции, невидимой другим созданиям. Проверить реальные будущие раунды, BLS, подписанные квитанции, законные ходы, отказ при подмене, повторные запросы, выход и новую эпоху реванша. Матрица: длинные нарды с ботом за оба цвета, короткие с ботом и длинные с двумя гостями. Ключи гостей хранятся только в защищённом временном файле, не в журнале.
8. В сборку Pages передать `FAIR_DICE_URL` и **настоящий** `FAIR_DICE_PUBLIC_KEY`, затем опубликовать совместимый клиент. Тестовый ключ из фикстур не является ключом production. Проверить опубликованные байты и закрепление ключа. Обычный `X-Client-Info` содержит совместимый маркер `nardu-fair-dice-v36`; это требование версии, не средство авторизации. Старая вкладка не может создать несовместимую новую комнату: получает понятное требование обновить страницу.
9. Только после проверок вызвать `configure_fair_dice_policy(true)` через защищённую service-role сессию. Политика действует на новые комнаты; уже начатые legacy партии не конвертируются посреди игры. После включения проверить ещё одну свежую контролируемую комнату и независимую браузерную проверку броска.

Откат: выключить политику **для новых комнат**, сохранить координатор и закреплённый клиент для уже защищённых партий либо корректно завершить их по согласованной процедуре. Не стирать журнал, не снимать ограничения с существующих защищённых комнат и не откатывать их к локальному RNG. Не удалять контейнер/маршрут до завершения таких партий. Полный restore базы допустим только как согласованное восстановление с учётом произошедших после backup действий.

Нужно отдельно нагрузочно проверить задержку, лимиты CPU/памяти и отказ источника. Избранные лимиты контейнера — защитные начальные настройки, не обещание пропускной способности.

## Воспроизведение проверок

```sh
npm ci
npm test
npm run build
node --test --test-concurrency=1 tests/fair-dice*.test.js
```

Тесты используют настоящий опубликованный quicknet раунд 1000, локальный тестовый Ed25519 ключ и изолированные HTTP/SQL-моки. Подтверждаются реальная BLS-проверка в Node и браузерном bundle, детерминированность, отказ при подделке, закрепление запроса, отсутствие переброса/fallback, авторизация, CAS, восстановление и серверная проверка ходов. Эти тесты не являются свидетельством уже выполненного production-развёртывания. В частности, реальный PostgreSQL rollback smoke до активации ещё обязателен.

Предварительный локальный прогон 18 сентября: 1164 теста, 1153 прошли, 0 ошибок, 11 Linux-специфичных пропусков на macOS. Сборка успешна; в настоящем браузере проверены полный положительный результат и отказ при подмене костей, раскрытие полной подписи/JSON/строки, оба языка и темы, экран 375×812 без горизонтального переполнения. Тестовый публичный ключ удалён из итоговой сборки. [Исторический снимок локальной проверки и SHA-256](fair-dice-verification-2026-09-18.json) относится к версии до исправлений, выявленных настоящим PostgreSQL, и до compatibility gate; его хеши не выдаются за хеши финального production-релиза.

Перед публикацией выполнены две PostgreSQL-проверки с откатом и реальные canary-партии через публичный HTTPS при выключенной общей политике: четыре комнаты, 16 подтверждённых бросков и 28 отклонённых попыток подмены/переброса. Обе подписи проверены, два законных хода, выход и реванш выполнены в каждой комнате. Измеренное ожидание в этой небольшой выборке: 7,727–9,330 секунды, среднее 8,744; это не нагрузочный benchmark. [Свидетельство production canary с полным публичным доказательством](fair-dice-production-canary-2026-09-18.json).

Спецификация независимого источника: [HTTP API](https://docs.drand.love/developer/http-api/), [криптография drand](https://docs.drand.love/docs/cryptography/), [модель безопасности](https://docs.drand.love/docs/security-model/). Локальная криптография — закреплённая версия `@noble/curves` 2.4.0 с локальной сборкой, без загрузки CDN-скриптов во время проверки.
